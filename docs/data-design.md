# データ設計：Trello風タスク管理アプリ

[requirements.md](requirements.md) を元にした、データまわりのラフな設計メモ。まだ実装前の段階なので、詳細を決め切らず「概要・例え」レベルで記載する。細かい部分は実装しながら随時追記・修正していく前提。

## 1. タスク1件のデータの形（イメージ）

タスク1件を、次のような「オブジェクト」（複数の情報をひとまとめにした箱、のようなデータの形）として持つイメージ。

```js
{
  id: 1,                                   // タスクを区別するための一意なID（保存時にデータベース側で自動採番する想定）
  title: "要件定義書を書く",               // タスクのタイトル（1〜100文字）
  status: "TODO",                          // 状態: "TODO"(未着手) / "DOING"(作業中) / "DONE"(完了)
  priority: "MEDIUM",                      // 優先度: "HIGH"(高) / "MEDIUM"(中) / "LOW"(低)。初期値は"MEDIUM"
  dueDate: "2026-08-20",                   // 期限日（YYYY-MM-DD形式の文字列）。未設定の場合はnull
  createdAt: "2026-08-12T10:00:00.000Z"    // 作成日時（同一列内の並び順に使う）
}
```

例え：タスク1件を「付箋1枚」だとすると、`id`は付箋の裏に貼る管理シール、`title`は付箋の本文、`status`はその付箋が今どの列に貼られているか、`priority`は付箋の色（重要度を表すマーカー）、`dueDate`は付箋の隅に書く締切メモ（書かないことも可）、`createdAt`はいつ書いたかのメモ、というイメージ。

`priority`（プライオリティ。優先度の意味）は3段階の文字列で持ち、画面表示のときに色へ変換する（例：HIGH→赤、MEDIUM→黄、LOW→緑）。`dueDate`（デュー・デート。期限日の意味）は日付の文字列で持ち、未設定のタスクは`null`（何もない、という値）にしておく。

`status`と`priority`の値は、バックエンド（Spring Boot）でJavaの`enum`（列挙型。決まった選択肢だけを表す型）として実装しており、`EnumType.STRING`という設定でデータベースに保存する方式にしたため、値は英大文字（"TODO"や"HIGH"など、Javaのenum定数名そのまま）で統一している。

タスク一覧は、このタスクオブジェクトを配列（リスト）にまとめて持つイメージ。

```js
[
  { id: "...", title: "タスクA", status: "TODO",  priority: "HIGH",   dueDate: "2026-08-20", createdAt: "..." },
  { id: "...", title: "タスクB", status: "DOING", priority: "MEDIUM", dueDate: null,          createdAt: "..." },
  { id: "...", title: "タスクC", status: "DONE",  priority: "LOW",    dueDate: "2026-08-10", createdAt: "..." },
]
```

このデータの形は、React（フロント）とSpring Boot（バックエンド）がAPIでやり取りするJSONの形、かつPostgreSQL（データベース）のテーブルに保存される1行分のイメージ、として共通で使う想定（[tech-stack.md](tech-stack.md)参照）。

## 2. データの保存方針（バックエンドAPI経由でPostgreSQLに保存）

[requirements.md](requirements.md) 5章のとおり、タスクデータの保存先はブラウザのlocalStorageではなく、バックエンドAPI経由のPostgreSQLデータベースに変更した。フロント（React）はデータを直接保存せず、バックエンド（Spring Boot）にAPI（決まった形でデータのやり取りをお願いする窓口、のようなもの）経由でお願いし、バックエンドが実際の読み書きを行う。

例え：データベースを「大きな保管庫」、APIを「保管庫の受付窓口」に例えると分かりやすい。フロント（利用者）は受付窓口（API）に「このタスクを保存して」「タスク一覧をちょうだい」とお願いするだけで、実際に保管庫（DB）に出し入れするのは窓口の奥にいる係員（バックエンド）の仕事、というイメージ。

- **データベース側**：タスク一覧を「tasksテーブル」のような表（スプレッドシートの1シートのようなもの）で持ち、表の1行が1タスクに対応する。列（カラム）は `id, title, status, priority, due_date, created_at, sort_order` のイメージで、1章のオブジェクトの項目とほぼ対応する
- **並べ替え（`sortOrder`）**: 同一状態（列）内での表示順を表す整数値。列ごとに独立した連番（1, 2, 3...）で持ち、初期値は状態ごとに作成日時の昇順で採番する。並べ替え時は`PATCH /api/tasks/reorder`に状態とタスクIDの新しい並び順を渡し、その列内のタスクだけ振り直す
- **画面表示の流れ（ざっくり）**：
  1. 画面を開く → フロントがバックエンドに「タスク一覧をください」とお願いする（例：`GET /api/tasks`）
  2. バックエンドがDBからタスク一覧を取り出し、フロントにJSONで返す
  3. フロントは受け取った一覧を画面（カンバンボード）に表示する
- **作成・編集・削除・状態変更のとき**も同様に、フロントがバックエンドにお願い（例：作成は`POST /api/tasks`、編集や状態変更は`PUT /api/tasks/{id}`、削除は`DELETE /api/tasks/{id}`）を送り、バックエンドがDBを更新する、という流れになる
- 想定データ量は数十件程度（[requirements.md](requirements.md) 5章参照）で、特別な性能要件は求めていないため、まずは上記のようなシンプルなAPI構成で十分と考える

※ あくまで方針レベルのメモ。APIのURLの名前や項目名（キャメルケース／スネークケースなど）といった細部は、バックエンドの実装を進める中で決めていく前提。
